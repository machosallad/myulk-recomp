# Code map of MYULK.EXE

Generated by `python -I tools/delphi_map.py` (needs `capstone`). Output goes to `analysis/`.

Addresses are written `seg:offset`, where `seg` is the 1-based NE segment number and `offset` is hex within that segment.

## Outputs

| File | Contents |
|---|---|
| `analysis/classes.json` | All 206 classes: VMT location, parent, unit, instance size, virtual slots, published methods, published fields (component name + offset in the object), dynamic/message methods |
| `analysis/events.json` | For each of the 57 forms: component → event → handler name + code address (332 events, all resolved) |
| `analysis/program.json` | Program entry, unit initialization calls in order, `CreateForm` calls, and which units live in which segment |
| `analysis/globals.csv` | Global form variables in the data segment (seg 34), e.g. `57D4 Main TMain` |
| `analysis/symbols.csv` | 802 named code locations (methods, VMTs, unit inits, RTL entry points), ready to import into Ghidra |

## Program structure

- **Entry** `1:0002`: InitTask, then `System.InitSystem`, then 19 unit initializations, then 57 × `Application.CreateForm`, then `Application.Run` and `Halt`.
- **The forms are all created at startup.** `TAdvForm` is created first, so it becomes Delphi's main form. `TMain` (the game view) is the fifth form created.
- **Segments 1–22** hold the game's own code and **23–33** hold the Delphi VCL/RTL (Buttons, ExtCtrls, StdCtrls, Graphics, Menus, Controls, Forms, Printers, Classes, SysUtils, System). Segment 34 is the data segment.
- **Segments 3 and 12** contain no classes, so they're plain procedure units: likely the game's simulation and economy code. They are good early targets.

## Delphi 1 VMT layout (as found in this binary)

Offsets are relative to the VMT pointer. Near pointers point into the class's own segment.

```
-32 near TypeInfo      -24 near ClassName       -16 far DefaultHandler
-30 near FieldTable    -22 word InstanceSize    -12 far NewInstance
-28 near MethodTable   -20 far  Parent VMT       -8 far FreeInstance
-26 near DynamicTable                              -4 far Destroy
  0 far[] user virtual methods, up to the ClassName string
```

Method table: `word count, {far ptr, shortstring name}`. Field table: `word count, near classtab, {word offset, word class index, shortstring name}`. Far pointers are stored as NE relocations (`tools/ne.py`, `NEFile.relocations`).

## Ghidra

Requires Ghidra 12.2+ (default `C:\Tools\ghidra`, override with `GHIDRA_HOME`), JDK 25 and `capstone`.

```bash
python -I tools/delphi_map.py                          # classes, events, symbols
python -I tools/find_functions.py                      # extra function entry points
python -I tools/ghidra/headless.py import              # import + names + auto-analysis (~25 s)
python -I tools/ghidra/headless.py script ExportDecomp.java 1 22   # decompile game code (~15 s)
```

- **Project location:** `ghidra_project/` (gitignored). Open it in the Ghidra GUI to browse the code interactively.
- **Settings folder:** `headless.py` points Ghidra's settings folder into `ghidra_project/settings`, because with the default folder under `%APPDATA%` the OSGi framework fails to start ("The data file must be inside the data dir").
- **Address mapping:** NE segment N is the memory block `CodeN` at selector `0x1000 + (N−1)·8`, so `9:3C8F` is `1040:3c8f` in Ghidra. The data segment is `Data34` at `1108:0000`.
- **Names applied (`ApplySymbols.java`):** 596 named functions in class namespaces (`TFormMaShop::TillbakaClick`), 206 VMT labels and 57 form globals.
- **Hidden routines (`find_functions.py`):** many routines are only reached through procedure pointers (scene/hotspot tables), so auto-analysis can't find them. This script seeds entry points from far-pointer relocation targets and from the `55 89 E5` prologue. That raised game-code coverage from as low as 3% in some segments to 57–94%. The rest is string constants and class tables.
- **Decompiled output (`ExportDecomp.java`):** writes `decomp/segNN.c` plus `decomp/functions.csv`. This covers 2,353 functions in segments 1–22, and only 1 failed to decompile. `decomp/` is gitignored because it is derived from the original code.

### Library routine names

The game makes 3,846 calls into the VCL/RTL (segments 23–33). Of those calls, 3,473 (90%) now go to named routines. The names come from three sources:

1. **RTTI property accessors** (automatic, `delphi_map.py`): every published property's static or virtual getter and setter, e.g. `TControl.SetVisible`, `TGauge.SetProgress`, `TautoButton.SetBitMapUp`. A property that a subclass re-publishes is credited to the most basic ancestor whose code is in that segment.
2. **Dynamic tables** (automatic): Windows message handlers (`TCustomPanel.WMSize`, ...). VCL-internal messages are left generic (`CM_B00B`).
3. **Hand-identified routines** in `analysis/library_names.csv`: the most-called routines, each recognized from its decompiled body (the `evidence` column says how). This covers string helpers, `Move`, `Copy`, `Pos`, `Random`, `Round`, the `as` cast, constructor/destructor helpers, `TObject.Free`, `IntToStr`, `Format`, `TForm.Close`/`ShowModal`, canvas and picture routines, `TControl.Show`/`Hide`, and more. These names override generated ones.

`tools/ghidra/TopCallees.java` ranks the still-unnamed library routines by how often game code calls them and dumps their bodies to `decomp/top_callees.txt`. Use it to extend `library_names.csv`.

**Notable finding:** the game does arithmetic in Turbo Pascal's 6-byte `Real` type (`System.RealLoad` converts it for the FPU). To get bit-identical results, the C++ port needs a Real48 emulation, or at least to match its rounding.
